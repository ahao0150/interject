# 实验记录

所有数字都是实测跑出来的，脚本在 `experiments/`，日志在原始项目的 `logs/` 目录。
模型统一为 **Qwen2.5-1.5B-Instruct**（fp16，约 3 GB），单卡 RTX 3060 12 GB。

## 一、任务切换：插话能改掉主要工作吗

同一句 `写一首关于秋天的诗`，中途插入「停一下，不要写诗了，改成写一篇关于秋天的散文」。
`seed=1234`，`max_new_tokens=220`。

| 组 | 投递 → 实际插入 | 结果 | 平均行长 | 主动交代 |
|---|---|---|---|---|
| A 基线（不插话） | — | 纯诗 20 行 | 9.8 | — |
| B 早插 | 第 8 → 14 token | 干净切换成散文 | 39.8 | ✓ |
| C 晚插 | 第 45 → 49 token | 能切，前留四行诗 | 30.1 | ✓ |
| D 极晚 | 第 100 → 101 token | 文体滑过去，**不承认换了任务** | 18.8 | ✗ |
| E 换领域 | 第 20 → 26 token | 诗 → 可运行 Python 代码 | 26.7 | ✗ |

「平均行长」是个意外好用的指标：诗是短行（9.8 字/行），散文是长句（39.8），
中间态就是 18.8。不用人工判读也能看出偏移程度。

**结论**：切换彻底程度随「已生成 token 数」衰减。前 15 个 token 内插几乎百分百转向；
到 100 token 还能改文体，但模型自己不再意识到这是任务变更。

## 二、注入措辞：哪句话能让模型「交代」

场景同上，极晚插入（第 100 token），3 个 seed。

| 措辞 | 交代率 | 典型反应 |
|---|---|---|
| `plain`（`（用户补充：xxx）`） | **1/3** | seed 777 反问「请告诉我您希望散文的主题是什么？」 |
| `brief`（加「先说明再直接照做」） | **3/3** | 三种不同的交代，都自然 |
| `strict`（加「立刻…不要停下来提问」） | 0/1（早插 1/1 但带敷衍） | 冒「请稍等片刻」 |

`brief` 三种 seed 的实际输出：

```
1234 → 好的，我明白了。以下是根据您的要求修改后的散文：
777  → 我明白了您的需求，现在为您写一篇关于秋天的散文：
2026 → 收到您的补充，明白了，请允许我为您改写成一篇关于秋天的散文。
```

**结论**：把指令放在插话正文里，而不是 system prompt 里。`brief` 是默认值。

## 三、system prompt 的两次失败

**第一版**（带具体例句「例如「好的，改成写散文」」）：

三组全部输出 `好的，改成写散文。` 然后 EOS，整轮 9 个字。
1.5B 把例句当成要复读的模板，而且它说完就停，插话都来不及插入（`step=None`）。

**第二版**（去掉例句，改三步指令）：

```
好的，我明白了你想要一首关于秋天的诗。知道了，我将改为写一篇关于秋天的散文。请稍等，我将为您创作。
```

交代有了，但一句散文没写就 EOS（49 字）。极晚那组直接反问用户要什么风格。

**结论**：system prompt 对这种「时刻相关的动作」无效。同样的内容放进插话正文立刻生效。

## 四、断句点策略：不切碎句子

初版「收到就插」会把句子切断：

```
我是Qwen，由阿里云我是一个预训练语言模型
```

改成「等句号再插」后：

```
红烧肉。
（用户补充：我不吃肉，是素食者）
烤蔬菜或豆腐料理都是不错的选择。
```

代价是插入点后移几个 token。实测单次 `waited_tokens` 在 0–24 之间，中位数约 8。
超过 24 个 token 还没等到句号就补一个强制插入 —— 但会产生「肥而不腻，。」这种多余标点，
所以中间加了一级「逗号处等够 8 个 token 就插」的软边界。

## 五、性能与显存

| 项 | 数值 | 说明 |
|---|---|---|
| 生成速度 | 16–20 tok/s | Qwen2.5-1.5B fp16，单卡 3060 |
| 显存峰值 | 4.3 GB / 12 GB | 含模型 3 GB |
| 插入开销 | < 1 token 的时间 | 只 forward 新增的几个 token |
| 首轮加载 | 约 30 秒 | 之后常驻 |

一个反面数据：漏掉 `@torch.inference_mode()` 时，PyTorch 分配到 **46 GiB** 后 OOM。
这是本项目最贵的一课 —— 表面症状是「模型生成到一半停住了」。

## 六、早期验证：小模型上的结论

最早用 26M / 64M 的 MiniMind 验证机制，四组对照实验的结论是：

- 非阻塞注入**确实省时间**：2.259s vs 2.477s（阻塞模式实际等了 0.349s）
- 噪音忽略率 93.3%，显存峰值 0.13 GB
- 但「采纳相关感知」这条**没过**：微调前后采纳率都是 4/30，完全一样

原因不是框架，是模型容量。64M 能收到插话，但不会因此改变已经形成的话语走向。
完整报告见 [legacy/MINIMIND-REPORT.md](legacy/MINIMIND-REPORT.md)。

换成 1.5B 之后，同一个机制立刻有了肉眼可见的效果 —— 这条对比正好说明
「瓶颈在模型能力，不在框架」。

## 七、可复现

```bash
# 任务切换（5 组对照）
python experiments/task_switch.py --model ./models/qwen2.5-1.5b

# 措辞对照（3 种 × 2 场景）
python experiments/inject_style.py --model ./models/qwen2.5-1.5b

# 稳定性（3 个 seed）
python experiments/style_stability.py --model ./models/qwen2.5-1.5b
```

所有实验固定 `seed`，采样参数 `temperature=0.75, top_p=0.9, top_k=50, repetition_penalty=1.05`。
